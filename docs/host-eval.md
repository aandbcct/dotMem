# 各宿主工具实测：接入 memhub 前后的检索对照

一句话：**同一个模型、同一批只存在于记忆里的项目约定，5 个能无头运行的工具原生 0/5，接入 memhub 后全部 5/5。**

这一页回答两个问题：接入后工具真的能用上记忆吗（检索对照）；每个宿主的接线是否完整（集成链路）。公开评测见 [评测](benchmarks.md)。

## 检索对照

| 工具 | 原生 | +memhub |
|---|:---:|:---:|
| Claude Code | 0/5 | **5/5** |
| Codex | 0/5 | **5/5** |
| OpenCode | 0/5 | **5/5** |
| kimi-cli | 0/5 | **5/5** |
| kimi-code | 0/5 | **5/5** |

### 做法

- **同一个模型**：所有工具都走 `deepseek-v4.1-flash-external`，非思考。Claude Code 经代理无法完全关闭思考（代理要求带 `effort` 就必须开自适应思考），只能用 `--effort low`。
- **每个工具两条臂**：原生，和 `install-host` 装好 memhub 的版本。两条臂各用一个全新的临时 `HOME` 和空工作目录，唯一差别是 memhub。
- **记忆只放在隔离的 Core 里**：三条项目约定写入一个独立的 Hub Core，原生臂既查不到，也猜不出。
- **三道题，共 5 个关键词，机械打分**，回答里出现关键词才算命中：

| 问题 | 关键词 |
|---|---|
| 压测项目的内部代号叫什么？接口超时统一设成几秒？ | 代号、`7.3` |
| 项目的错误码前缀是什么？数据库连接串通过哪个环境变量注入？ | `QX9`、`QX_DSN` |
| 合并代码之前必须先跑哪条命令？ | 带随机编号的 `make smoke-…` |

- **原生臂被污染就作废重跑**：每次跑完统计该臂访问 Core 的次数，原生臂必须为 0。每个 +memhub 臂开始前，会清掉前面各臂捕获进库的对话，只保留这三条种子，避免一个工具召回另一个工具的答案。

### 结果

| 工具 | 原生命中 | +memhub 命中 | +memhub 召回次数 |
|---|:---:|:---:|:---:|
| Claude Code | 0/5 | 5/5 | 9 |
| Codex | 0/5 | 5/5 | 3 |
| OpenCode | 0/5 | 5/5 | 3 |
| kimi-cli | 0/5 | 5/5 | 3 |
| kimi-code | 0/5 | 5/5 | 6 |

所有原生臂访问 Core 为 0 次。耗时在 15–100 秒之间，差别主要来自各工具自己的启动与工具调用，不是 memhub 的开销。

### 怎么读这个结果

- 它衡量的是**能不能用上只存在于记忆里的项目事实**。原生工具在空目录里没有任何线索，所以原生为 0 是预期的，不代表原生工具弱；真实项目里，约定如果写在代码或 `AGENTS.md` 里，原生也能查到。
- 没有衡量普通编码任务的效果，也没有比较不同工具之间的优劣。
- 每个臂只跑一次最终结果，题量小，用来确认"接线有效"，不是统计显著的结论。kimi-cli 另外重复跑过两次，都是 5/5。
- 验证脚本放在仓库的 `tmp/` 下，该目录不入库，暂不提供一键复现。

## 验证中发现并修复的问题

- **召回注入整体失败**：`remember` 和 MCP `memory_add` 写入的记忆没有 `memory_at`，召回出来的原始对话缺这个字段，提示词 hook 抛 `KeyError` 并被吞掉，那一轮不注入任何记忆。Claude Code 的 +memhub 臂最初只有 3/5，就是因为这个。已修复：写入按到达时间记时，hook 也容忍无时间的记录。
- **skill 触发条件过窄**：skill 描述里去掉了"项目约定、代号、命令"这类触发场景后，kimi-cli 会不去检索；补回后连续两次 5/5。
